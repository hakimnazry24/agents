# ISO 14971:2019 — Risk management (key RM)

**Source:** checked against the full text of ISO 14971:2019 (third edition). Clause numbers are exact.

**In plain words:** decide up front how much risk is acceptable, list everything that could cause harm, estimate how bad and how likely each harm is, reduce each risk (design first, warnings last), check that each fix is in place and works, weigh what is left against the benefit, tell users about the risks that remain, and keep collecting field information after release. Every other standard feeds into it.

**What the standard covers that matters for INNUTRIRE:**
- **Scope includes software and data security.** Clause 1 names software as a medical device and data and systems security risks. "Harm" includes damage to data and property (3.3), so a breach or corrupted record is a harm to analyse, not only an IT problem.
- **The chain is hazard → sequence of events → hazardous situation → harm** (Annex C). A risk can only be estimated once the hazardous situation is named. Example for INNUTRIRE: wrong unit (hazard) → nurse types weight in lb (event) → model gets a wrong feature (hazardous situation) → patient is underfed (harm).
- **Hazards relevant to software** (Annex C, Table C.1, performance-related): data access, availability, confidentiality, transfer and integrity; diagnostic information (examination result, patient identity); functionality (alarm, critical performance, measurement). Table C.2 adds use-related events (unclear presentation of results, wrong patient selected, slips and lapses) and security events (exposed ports, unencrypted data, exploitable vulnerabilities, updates without authenticity checks).
- **Risk control priority order** (7.1): 1) inherently safe design, 2) protective measures in the device, 3) information for safety and training. A warning does not replace a design fix when a design fix is practicable.
- **Two verifications per control** (7.2): that the control is implemented, and that it actually reduces the risk.
- **Residual risk must be disclosed** to users in the accompanying documentation (8), e.g. instructions for use or on-screen information.
- **Post-production** (10) must actively collect information from users, people who install and maintain the device (hospital IT), the supply chain (third-party software, calorimeter and tablet makers), public sources (CVEs, recalls of similar devices) and the state of the art, then review it for new hazards.

**Relation to INNUTRIRE:** example hazards are a wrong calculation (BMI class, severity scores, injury factor), a wrong unit, the wrong patient selected, data lost while offline, an AI prediction far from the real need for some patient groups, records changed by an attacker or leaked, and the server being down at the bedside.

Check IDs RM-01 to RM-08 keep the same meaning as earlier versions of this checklist, because cards on the Trello board are matched by ID. New checks get new numbers.

### RM-01 Risk management file exists and is traceable
- **Applies to:** all (normally kept once for the whole system; a repo may link to it)
- **Clause:** 4.5 (also 7.5, 7.6)
- **Look for:** `docs/**/risk*`, `*hazard*`, `*fmea*`, risk tables (`.md`, `.csv`, `.xlsx`), links to them in `README`, `CLAUDE.md` or `AGENTS.md`, and the shared compliance repo (see `innutrire-context.md`). For each hazard the file should trace to: its risk analysis, its evaluation, the controls and their verification, and the residual risk result. It should also show a review that controls did not add new risks (7.5) and that every hazardous situation was covered (7.6).
- **Met:** a file with per-hazard traceability. **Partial:** a file or table exists but rows lack controls, verification or residual risk. **Gap:** nothing found.
- **Severity if not met:** High

### RM-02 Intended use and reasonably foreseeable misuse are written down
- **Applies to:** all
- **Clause:** 5.2
- **Look for:** an "intended use" or "intended purpose" statement covering medical indication, patient population, user profile, use environment and operating principle (3.6 Note 1), plus a list of foreseeable misuse (e.g. using it on non-ICU or paediatric patients, treating the prediction as a final prescription, typing values in the wrong unit).
- **Met:** intended use and misuse both written. **Partial:** intended use only, or only a general product description. **Gap:** none.
- **Severity if not met:** High

### RM-03 Hazards and hazardous situations identified for safety-critical code
- **Applies to:** backend, tablet-app
- **Clause:** 5.3, 5.4
- **Look for:** for each safety-critical area in `innutrire-context.md`, a record of what could go wrong in normal and fault conditions, and the sequence of events that leads to a hazardous situation: docs, risk table rows, test names describing failure cases, or issue references. Characteristics related to safety (5.3) should have stated limits, e.g. accepted ranges for height, weight, temperature and vitals.
- **Met:** hazards and limits documented for each area. **Partial:** some areas, or hazards without the event sequence. **Gap:** none.
- **Severity if not met:** High

### RM-04 Risk controls exist in code for known hazards, design first
- **Applies to:** backend, tablet-app
- **Clause:** 7.1, 7.2
- **Look for:** input range validation (height, weight, temperature, vitals), unit handling, rejecting impossible values, safe defaults, clear error messages, and a server-side check that does not rely only on the tablet.
  - backend: `ml_model_service.py` and the prediction views
  - tablet-app: the keyboards, score forms and REE calculation

  Check the priority order: if the only control for a hazard is a warning or a manual instruction while a design control (blocking the value, forcing a unit) was practicable, the control is weaker than the standard expects.
- **Met:** inputs are range-checked on both sides by design. **Partial:** on one side only, only some fields, or warning-only where design control was possible. **Gap:** unchecked numeric inputs reach the model.
- **Severity if not met:** High

### RM-05 Risk controls are verified by tests
- **Applies to:** backend, tablet-app
- **Clause:** 7.2 (verification of implementation and of effectiveness)
- **Look for:** tests that cover boundary and invalid inputs, unit conversion, BMI and temperature classes, the injury factor, and severity score calculations. A test that only shows the code path exists proves implementation; a test that shows the bad value is actually stopped or corrected proves effectiveness.
- **Met:** tests for each control, showing it works. **Partial:** some controls, or only happy-path tests. **Gap:** none.
- **Severity if not met:** High

### RM-06 AI model limits are known and stated
- **Applies to:** backend
- **Clause:** 5.3 (safety-related characteristics and their limits), 8 (disclosure of residual risk)
- **Look for:** documented model performance (error in kcal), the data it was trained on, the patient groups and input ranges it was not validated on, and whether the app or API shows a warning, range check or confidence measure when an input falls outside them.
- **Met:** limits documented and surfaced to users. **Partial:** documented only. **Gap:** neither.
- **Severity if not met:** High

### RM-07 Overall residual risk and benefit-risk argument
- **Applies to:** all (usually outside the repo)
- **Clause:** 7.4, 8
- **Look for:** a statement weighing INNUTRIRE's benefit (accuracy versus existing predictive equations, time saved) against all remaining risks together, using the method and criteria set in the risk management plan.
- **Met:** present. **Gap:** missing. Use `Outside repo` if the repo cannot hold it.
- **Severity if not met:** Medium

### RM-08 Production and post-production information is collected and reviewed
- **Applies to:** backend, monitoring
- **Clause:** 10.1–10.4
- **Look for:** active collection of field information that could reveal new risks, and a review loop that feeds it back into the risk file. Sources the standard names: users (feedback channel, problem reports), people who install and maintain it (hospital IT, deployment logs), the supply chain (third-party software updates, calorimeter and tablet makers), public information (CVEs, recalls or incidents with similar devices) and the state of the art. In code this looks like error logging, Moniteer health and accuracy tracking, and comparison of predicted against gold-standard REE.
- **Met:** collected from several sources and reviewed. **Partial:** data collected but no review loop, or only one source. **Gap:** none.
- **Severity if not met:** Medium

### RM-09 Risk management plan with acceptability criteria
- **Applies to:** all (usually outside the repo or in the shared compliance repo)
- **Clause:** 4.2, 4.4
- **Look for:** a plan for INNUTRIRE that sets: scope and life cycle phases; who is responsible and who reviews; criteria for accepting a risk (including when probability can't be estimated, which is normal for software faults); the method and criteria for judging overall residual risk; how controls will be verified; and how field information will be collected. Also the management policy the criteria come from, and a record of plan changes.
- **Met:** plan with criteria exists. **Partial:** criteria or roles only. **Gap:** none. **Outside repo** if it is kept elsewhere; ask for it.
- **Severity if not met:** High

### RM-10 Each hazardous situation has an estimated and evaluated risk
- **Applies to:** all (usually in the risk file)
- **Clause:** 5.5, 6
- **Look for:** a written severity scale and probability scale (qualitative is fine), a severity and probability for each hazardous situation, and a decision against the plan's criteria on whether control is needed. Where probability can't be estimated, the possible consequences are listed instead.
- **Met:** scales defined and applied to every row. **Partial:** scales defined but not applied, or applied to some rows. **Gap:** none.
- **Severity if not met:** Medium

### RM-11 Data and security hazards are part of the risk analysis
- **Applies to:** all
- **Clause:** 1 (scope), 5.4, Annex C (Tables C.1, C.2)
- **Look for:** whether the risk analysis treats patient-data confidentiality, integrity, availability and transfer, wrong patient identity, exposed ports, unencrypted data, exploitable dependencies and unverified updates as hazards with a link to patient harm (e.g. a corrupted record leads to a wrong energy target). Security findings that live only in a separate security list, with no tie to harm, count as Partial.
- **Met:** security and data hazards in the risk file with their harms. **Partial:** tracked separately without a harm link. **Gap:** not considered.
- **Severity if not met:** High

### RM-12 Significant residual risks are disclosed to users
- **Applies to:** tablet-app (and any user documentation shipped with it)
- **Clause:** 8
- **Look for:** instructions for use, an in-app help or about page, or release notes for hospitals that tell users the remaining significant risks: model limits, the need for clinical judgement, known issues, what happens when offline. Check `frontend_innutrire` docs and screens.
- **Met:** disclosed in documentation users actually get. **Partial:** stated only in developer docs. **Gap:** none.
- **Severity if not met:** Medium

### RM-13 Risk management review before release
- **Applies to:** all (usually outside the repo)
- **Clause:** 9
- **Look for:** a risk management report, or a release checklist or workflow step, confirming before a release goes to hospitals that the plan was carried out, overall residual risk is acceptable, and field-information collection is in place.
- **Met:** report or release gate exists. **Partial:** release checklist without the risk items. **Gap:** none. **Outside repo** if kept elsewhere.
- **Severity if not met:** Medium
