# ISO 14971:2019 — Risk management (key RM)

**In plain words:** list everything that could harm a patient, estimate how bad and how likely it is, reduce each risk, check that the fix works, and keep watching after release. Every other standard feeds into it.

**Relation to INNUTRIRE:** example hazards are a wrong calculation (BMI class, severity scores, injury factor), a wrong unit, data lost while offline, an AI prediction far from the real need for some patient groups, records changed by an attacker, and the server being down at the bedside.

---

### RM-01 Risk management file exists
- **Applies to:** all (normally kept in one place; a repo may link to it)
- **Clause:** 4.5
- **Look for:** `docs/**/risk*`, `*hazard*`, `*fmea*`, risk tables (`.md`, `.csv`, `.xlsx`), and links to them in `README`, `CLAUDE.md` or `AGENTS.md`.
- **Met:** a risk file or a link to one. **Partial:** risks are mentioned in scattered docs. **Gap:** nothing found.
- **Severity if not met:** High

### RM-02 Intended use is written down
- **Applies to:** all
- **Clause:** 5.2
- **Look for:** an "intended use" or "intended purpose" statement: who uses INNUTRIRE, for which patients, and what decision it supports. Check `README`, `docs/` and `CLAUDE.md`.
- **Met:** explicit statement. **Partial:** only a general product description. **Gap:** none.
- **Severity if not met:** High

### RM-03 Hazards identified for safety-critical code
- **Applies to:** backend, tablet-app
- **Clause:** 5.4
- **Look for:** for each safety-critical area in `innutrire-context.md`, any record of what could go wrong: comments, docs, test names describing failure cases, or issue references.
- **Met:** hazards documented for each area. **Partial:** some areas. **Gap:** none.
- **Severity if not met:** High

### RM-04 Risk controls exist in code for known hazards
- **Applies to:** backend, tablet-app
- **Clause:** 7.1, 7.2
- **Look for:** input range validation (height, weight, temperature, vitals), unit handling, rejecting impossible values, safe defaults, clear error messages, and a server-side check that does not rely only on the tablet.
  - backend: `ml_model_service.py` and the prediction views
  - tablet-app: the keyboards, score forms and REE calculation
- **Met:** inputs are range-checked on both sides. **Partial:** on one side only, or only some fields. **Gap:** unchecked numeric inputs reach the model.
- **Severity if not met:** High

### RM-05 Risk controls are verified by tests
- **Applies to:** backend, tablet-app
- **Clause:** 7.3
- **Look for:** tests that cover boundary and invalid inputs, unit conversion, BMI and temperature classes, the injury factor, and severity score calculations.
- **Met:** tests for each control. **Partial:** some. **Gap:** none.
- **Severity if not met:** High

### RM-06 AI model limits are known and stated
- **Applies to:** backend
- **Clause:** 5.5, 8
- **Look for:** documented model performance (error in kcal), the data it was trained on, the patient groups it was not validated on, and whether the app or API exposes a warning or confidence measure.
- **Met:** limits documented and surfaced to users. **Partial:** documented only. **Gap:** neither.
- **Severity if not met:** High

### RM-07 Overall residual risk and benefit-risk argument
- **Applies to:** all (usually outside the repo)
- **Clause:** 8
- **Look for:** a statement comparing INNUTRIRE's benefit (accuracy versus existing equations) with its remaining risks.
- **Met:** present. **Gap:** missing. Use `Outside repo` if the repo cannot hold it.
- **Severity if not met:** Medium

### RM-08 Production and post-production monitoring
- **Applies to:** backend, monitoring
- **Clause:** 10
- **Look for:** collection of field information that could reveal new risks: error logging, Moniteer health and accuracy tracking, feedback channels, and comparison of predicted against gold-standard REE.
- **Met:** monitored and reviewed. **Partial:** data collected but no review loop. **Gap:** none.
- **Severity if not met:** Medium
