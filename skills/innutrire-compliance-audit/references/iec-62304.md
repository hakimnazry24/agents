# IEC 62304:2006+A1:2015 — Medical device software lifecycle (key SW)

**In plain words:** a controlled way to plan, build, test, release and maintain medical software, with records showing it was done. How much is required depends on the software safety class: A (no injury possible), B (non-serious injury), C (death or serious injury). INNUTRIRE is provisionally Class B, to be confirmed by risk analysis.

---

### SW-01 Software safety class assigned
- **Applies to:** backend, tablet-app, monitoring
- **Clause:** 4.3
- **Look for:** a documented safety class (A, B or C) and the reason for it.
- **Met:** class plus reasoning. **Gap:** none.
- **Severity if not met:** Medium

### SW-02 Software development plan
- **Applies to:** all
- **Clause:** 5.1
- **Look for:** a documented process: branching and review rules, tools, standards followed, how releases happen. `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING*` and `README` partly count.
- **Met:** a plan covering lifecycle, tools and reviews. **Partial:** scattered notes. **Gap:** none.
- **Severity if not met:** Medium

### SW-03 Written software requirements
- **Applies to:** backend, tablet-app, monitoring
- **Clause:** 5.2
- **Look for:** a requirements document or structured list (functional, performance, safety, security and usability requirements), in `docs/` or similar. API docs and README endpoint tables count as partial.
- **Met:** requirements with IDs. **Partial:** informal descriptions. **Gap:** none.
- **Severity if not met:** High

### SW-04 Software architecture documented
- **Applies to:** backend, tablet-app, monitoring
- **Clause:** 5.3
- **Look for:** an architecture description (components, interfaces, data flow) and where third-party software sits in it. A repo layout in `CLAUDE.md` or `README` counts as partial.
- **Met:** components and interfaces. **Partial:** folder layout only. **Gap:** none.
- **Severity if not met:** Medium

### SW-05 Unit verification and tests
- **Applies to:** backend, tablet-app, monitoring
- **Clause:** 5.5
- **Look for:** test folders and files, and the share of safety-critical modules (from `innutrire-context.md`) that have tests. Name any critical module with no test.
- **Met:** every critical module tested. **Partial:** some. **Gap:** little or no testing.
- **Severity if not met:** High

### SW-06 Tests run automatically on every change
- **Applies to:** backend, tablet-app, monitoring, infrastructure, provisioning
- **Clause:** 5.6, 5.7
- **Look for:** `.github/workflows/*` jobs that run tests, lint or validation on pull requests or pushes.
- **Met:** tests run on every pull request. **Partial:** lint only, or run only on release. **Gap:** no CI.
- **Severity if not met:** High

### SW-07 Requirements traced to tests
- **Applies to:** backend, tablet-app
- **Clause:** 5.7.4
- **Look for:** a link between requirement IDs and tests: a trace table, or test names and docstrings that reference requirements.
- **Met:** a trace exists. **Gap:** none (always a Gap if SW-03 is a Gap).
- **Severity if not met:** Medium

### SW-08 Controlled release with version and notes
- **Applies to:** backend, tablet-app, monitoring
- **Clause:** 5.8
- **Look for:** semantic version numbers, `CHANGELOG.md`, release workflow, tagged releases (`git tag`), and a record of known open issues at release time.
- **Met:** versioned releases, changelog and known-issue record. **Partial:** versions and changelog without known issues. **Gap:** none.
- **Severity if not met:** Medium

### SW-09 Third-party software (SOUP) list
- **Applies to:** backend, tablet-app, monitoring
- **Clause:** 5.3.3, 8.1.2
- **Look for:** pinned dependency versions (lock files, `==` pins) and a SOUP list naming each library's purpose and known issues. Pinned manifests alone count as partial.
- **Met:** SOUP list with purpose and known issues. **Partial:** pinned versions only. **Gap:** unpinned dependencies.
- **Severity if not met:** Medium

### SW-10 Configuration management
- **Applies to:** all
- **Clause:** 8
- **Look for:** git history, protected main branch (from workflow or docs), build reproducibility (lock files, Dockerfile pins, PyInstaller spec), and versioned AI model artefacts (model file name or metadata with a version and training data reference).
- **Met:** all of these, including the model version. **Partial:** code versioned but the model or build is not. **Gap:** none.
- **Severity if not met:** Medium

### SW-11 Problem resolution process
- **Applies to:** all
- **Clause:** 9
- **Look for:** an issue tracker referenced from the repo (the Trello links in PR templates or docs), bug-fix commits that reference tickets, and a regression test added with each fix.
- **Met:** tracked and linked, with tests. **Partial:** tracked but not linked. **Outside repo:** tracking happens only on Trello with no link.
- **Severity if not met:** Low

### SW-12 Maintenance process
- **Applies to:** backend, tablet-app, monitoring
- **Clause:** 6
- **Look for:** how field feedback and change requests are handled after release: deploy and promote workflows, rollback, and a documented update procedure for hospitals.
- **Met:** a documented procedure including rollback. **Partial:** automation exists but is undocumented. **Gap:** none.
- **Severity if not met:** Medium
