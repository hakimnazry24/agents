# IEC 62304:2006+AMD1:2015 (edition 1.1) — Medical device software life cycle (key SW)

**Source:** checked against the full text of IEC 62304:2006 + Amendment 1:2015, consolidated edition 1.1 (2015-06). Clause numbers are exact.

**In plain words:** plan the software work, write down what the software must do, describe how it is built, test it at each level, release it in a controlled way, keep it under version control, track every problem, and keep doing all of this after release. How much paperwork and testing is required depends on the software safety class (A, B or C), which comes from the worst harm the software could contribute to. The standard covers the software only; validating the finished product for its clinical purpose is outside it (1.2).

**What the standard covers that matters for INNUTRIRE:**
- **Software safety class decides the work** (4.3). Class A: no injury possible. Class B: non-serious injury possible. Class C: death or serious injury possible. When judging this, a software failure is assumed to happen (probability 100%). Since Amendment 1, risk controls outside the software (another independent system, a hardware control, or a clinical procedure such as a dietitian checking the recommendation) can be counted before choosing the class. The class and its reasoning must be in the risk management file (4.3 c).
- **Until a class is recorded, Class C rules apply** (4.3 g). This is why the checks below include Class C-only items: an unrecorded "provisionally Class B" does not lower the bar. For INNUTRIRE, a wrong energy target for an ICU patient could plausibly be argued as either B or C depending on how much clinical review is relied on, so the decision must be written down with reasons. Once a class is recorded, mark Class C-only checks `Not applicable` if the class is A or B.
- **Parts of the software can have different classes** (4.3 d–f), e.g. Moniteer or the XAI screens lower than the REE calculation, but only with a written reason that explains how the parts are kept apart (segregation) so a fault in one can't affect the other. Without that, every part takes the highest class.
- **Requirements by class** (Annex A, Table A.1, informative; the normative text tags each requirement):
  - All classes: development plan basics (5.1.1–5.1.3, 5.1.6–5.1.9), requirements (5.2 except 5.2.3), implementing units (5.5.1), system testing (5.7), release basics (5.8.1, 5.8.2, 5.8.4, 5.8.7, 5.8.8), maintenance (Clause 6), safety check of changes (7.4.1), configuration management (Clause 8), problem resolution (Clause 9).
  - Class B and C add: integration plan, control of supporting tools, common-defect procedure (5.1.5, 5.1.10–5.1.12), risk controls in requirements (5.2.3), architecture and SOUP requirements (5.3 except 5.3.5), splitting into units (5.4.1), unit verification (5.5.2, 5.5.3, 5.5.5), integration testing (5.6), evaluating known bugs and documenting how the release was built (5.8.3, 5.8.5, 5.8.6), software risk analysis (7.1–7.3, 7.4.2, 7.4.3).
  - Class C only adds: development standards, methods and tools (5.1.4), segregation for risk control (5.3.5), detailed design (5.4.2–5.4.4), extra unit acceptance criteria such as boundary conditions and fault handling (5.5.4).
- **Amendment 1 changes worth knowing:** a new procedure to find and avoid common defects of the chosen programming language (5.1.12); security and IT-network requirements named in the requirements content (5.2.2 e, j); segregation now Class C only (5.3.5); detailed design of each unit now Class C only (5.4.2); release must guarantee delivery to the point of use without corruption or unauthorised change (5.8.8); problem reports must state criticality, e.g. effect on safety or security (9.1); a route for software already on the market without full records ("legacy software", 4.4).
- **SOUP** ("software of unknown provenance": any third-party library or tool not made for this device, such as Django, scikit-learn, PySide6) must be listed with name, maker and exact version (8.1.2), have its needed functions and required platform stated (5.3.3, 5.3.4), have its published bug lists checked for hazards (7.1.3), and have a procedure for upgrades, patches and obsolescence (6.1 f). SOUP failure is a named cause of hazardous situations (7.1.2 c).
- **Links to other standards:** the quality management system (4.1) is checked under ISO 13485 and the overall risk process (4.2) under ISO 14971. Clause 7 here adds the software-specific part: which software items can cause harm, why, and the trace from hazard to test.

**Relation to INNUTRIRE:** the backend (ML inference, feature preparation, injury factor) and the tablet app (data entry, score forms, offline cache) are medical device software. Moniteer, the tablet setup scripts and the server setup carry or install that software and patient data; whether each counts as medical device software, a separately classed item, or a supporting tool must be decided and recorded (SW-01). The deployed AI model file and its training data are configuration items like any code.

Check IDs SW-01 to SW-12 keep the same meaning as earlier versions of this checklist, because cards on the Trello board are matched by ID. New checks get new numbers.

### SW-01 Software safety class assigned
- **Applies to:** all (normally one record for the whole system in the risk file or shared compliance repo; a repo may link to it)
- **Clause:** 4.3 a), c)–g) [Class A, B, C]
- **Look for:** a recorded safety class (A, B or C) for each software system (backend, tablet app) with the reasoning: the worst harm it could contribute to, assuming the software fails, and any outside risk controls counted (e.g. clinician review). If parts are given a lower class (Moniteer, XAI), a written reason explaining how they are kept apart. A recorded decision on whether Moniteer, the tablet setup scripts and the server setup are medical device software, separately classed items, or supporting tools. A note like "provisionally Class B" with no reasoning counts as not assigned.
- **Met:** class and reasoning recorded for every software system, plus the scope decision. **Partial:** a class stated without reasoning, or only for some systems, or no scope decision for the supporting repos. **Gap:** none recorded (then audit every check against Class C, per 4.3 g).
- **Severity if not met:** High

### SW-02 Software development plan
- **Applies to:** all (normally one plan, often in the shared compliance repo)
- **Clause:** 5.1.1–5.1.11 [5.1.1–5.1.3, 5.1.6–5.1.9: Class A, B, C; 5.1.5, 5.1.10, 5.1.11: Class B, C; 5.1.4: Class C]
- **Look for:** one plan (or a set of plans that reference each other) that names: the life cycle model and processes used; the deliverables of each step; how requirements, tests and risk controls are traced; how configuration and change management work, including SOUP and development tools; how problems are handled at each stage; what gets verified, when, and against which acceptance criteria; how risks (including SOUP risks) are managed; which documents are produced, their purpose, and who writes, reviews and approves them; which items go under configuration control and when; an integration and integration-testing plan; and the coding standards, methods and tools used (Class C). The plan must reference the system requirements and be kept up to date (5.1.2, 5.1.3). `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING*`, PR templates and `README` cover parts of this but are not a plan on their own.
- **Met:** a maintained plan covering these points. **Partial:** scattered notes that cover some points. **Gap:** none.
- **Severity if not met:** Medium

### SW-03 Written software requirements
- **Applies to:** backend, tablet-app, monitoring (a system-wide document in the shared compliance repo also counts)
- **Clause:** 5.2.1–5.2.6 [Class A, B, C; 5.2.3: Class B, C]
- **Look for:** a requirements document or structured list with unique IDs covering, as relevant (5.2.2): functions and performance; inputs and outputs with data types, ranges, limits and defaults (e.g. accepted height, weight, temperature, vitals); interfaces to other systems (tablet ↔ backend API, Moniteer agent API); alarms, warnings and on-screen messages; security (sign-in, permissions, audit trail, data integrity in transit); usability needs; data and database needs; installation and acceptance at the hospital; operation and maintenance; IT-network behaviour (protocols, what happens when the network or server is down); user maintenance; regulatory needs. Risk controls done in software must appear as requirements (5.2.3). Evidence that requirements were reviewed: no contradictions, unambiguous, testable, traceable to a source (5.2.6), and that the risk analysis was revisited once requirements were set (5.2.4). API docs and README endpoint tables count as partial.
- **Met:** requirements with IDs covering the relevant categories, including risk controls, with a review record. **Partial:** informal descriptions, missing categories, or no IDs. **Gap:** none.
- **Severity if not met:** High

### SW-04 Software architecture documented
- **Applies to:** backend, tablet-app, monitoring
- **Clause:** 5.3.1, 5.3.2, 5.3.5, 5.3.6, 5.4.1 [Class B, C; 5.3.5: Class C]
- **Look for:** a document that breaks each software system into its software items (e.g. API views, ML service, injury factor, local cache, score forms), describes the interfaces between them and with outside parts (database, tablet OS, network, Moniteer), and shows where SOUP sits. Each item further split down to units (5.4.1; a unit can be a module or class, the team defines the level). For Class C, or when a lower class is claimed for some items: which separation between items is needed for safety and how it is made effective (5.3.5). A record that the architecture was checked against the requirements, including risk controls (5.3.6). A repo layout in `CLAUDE.md` or `README` counts as partial.
- **Met:** items, interfaces and SOUP placement documented and checked against requirements. **Partial:** folder layout or diagram without interfaces, or no verification record. **Gap:** none.
- **Severity if not met:** Medium

### SW-05 Unit verification and tests
- **Applies to:** backend, tablet-app, monitoring
- **Clause:** 5.5.2–5.5.5 [5.5.2, 5.5.3, 5.5.5: Class B, C; 5.5.4: Class C]
- **Look for:** tests (or reviews) for each safety-critical unit in `innutrire-context.md`; written acceptance criteria for units (e.g. "matches requirement, follows coding standard"); recorded results. For Class C, criteria for boundary conditions, fault handling, data flow and variable initialisation (5.5.4), e.g. tests at the exact limits of input ranges. Name any critical module with no test.
- **Met:** every critical unit verified against stated criteria, with results kept. **Partial:** some units, or tests without stated criteria. **Gap:** little or no testing.
- **Severity if not met:** High

### SW-06 Tests run automatically on every change
- **Applies to:** backend, tablet-app, monitoring, infrastructure, provisioning
- **Clause:** 5.6.6, 5.7.3, 8.2.3 [5.6.6: Class B, C; 5.7.3, 8.2.3: Class A, B, C]
- **Look for:** `.github/workflows/*` jobs that run tests, lint or validation on pull requests or pushes, so a change can't silently break earlier work (regression testing) and changed code is re-verified before merge.
- **Met:** tests run on every pull request. **Partial:** lint only, or run only on release. **Gap:** no CI.
- **Severity if not met:** High

### SW-07 Requirements traced to tests
- **Applies to:** backend, tablet-app
- **Clause:** 5.1.1 c), 5.7.1, 5.7.4 [Class A, B, C]
- **Look for:** a system-level test set that covers every software requirement, each test with its input, expected result and pass/fail criterion (5.7.1), and a recorded link from each requirement to the test or other verification that covers it (5.7.4): a trace table, or test names and docstrings that cite requirement IDs. Also evidence that the test approach was judged adequate.
- **Met:** every requirement traced to a test with a pass result. **Partial:** some requirements traced. **Gap:** none (always a Gap if SW-03 is a Gap).
- **Severity if not met:** Medium

### SW-08 Controlled release with version and known-issue record
- **Applies to:** backend, tablet-app, monitoring
- **Clause:** 5.8.1–5.8.6 [5.8.1, 5.8.2, 5.8.4: Class A, B, C; 5.8.3, 5.8.5, 5.8.6: Class B, C]
- **Look for:** a unique version per release (semantic versions, `git tag`, `CHANGELOG.md`, release workflow); a check that all verification finished before release; a list of known open bugs ("residual anomalies") at release time, each judged for whether it could cause unacceptable risk (5.8.3); a record of how and in what environment the release was built (5.8.5, often the release workflow itself); confirmation that the plan's activities and documents are complete.
- **Met:** versioned releases with changelog, known-issue list with risk judgement, and build record. **Partial:** versions and changelog without known issues or without the risk judgement. **Gap:** none.
- **Severity if not met:** Medium

### SW-09 Third-party software (SOUP) list
- **Applies to:** backend, tablet-app, monitoring
- **Clause:** 8.1.2 [Class A, B, C]; 5.3.3, 5.3.4, 7.1.3 [Class B, C]
- **Look for:** pinned dependency versions (lock files, `==` pins, base image tags) and a SOUP list giving each item's name, maker and exact version (8.1.2), including standard libraries and runtimes (Python, Qt). For Class B and C also: what each item must do for INNUTRIRE and any performance needs (5.3.3), the platform it needs (5.3.4), and a record that the maker's published bug list or security advisories for that version were reviewed for hazards (7.1.3). Pinned manifests alone count as partial.
- **Met:** SOUP list with version, maker, purpose, requirements and reviewed known issues. **Partial:** pinned versions only, or a list without purpose or known-issue review. **Gap:** unpinned dependencies.
- **Severity if not met:** Medium

### SW-10 Configuration management: everything that makes a release is versioned
- **Applies to:** all
- **Clause:** 8.1.1, 8.1.3, 8.3 [Class A, B, C]; 5.1.10, 5.1.11 [Class B, C]
- **Look for:** a scheme that gives every configuration item a unique identity and version (8.1.1): code (git), documents, SOUP, the deployed AI model file (version in name or metadata, plus a reference to the training data and code that produced it), Docker images, PyInstaller spec, OS and Python versions. A record of which item versions make up each deployed system (8.1.3), e.g. backend version + model version + tablet app version per hospital. Tools and settings that could affect the product kept under control (5.1.10): CI runner images, build scripts, compiler and packager versions. History of each item retrievable (8.3).
- **Met:** all of these, including the model and build tools. **Partial:** code versioned but the model, build tools or system configuration record is not. **Gap:** none.
- **Severity if not met:** Medium

### SW-11 Problems tracked and linked to approved code changes
- **Applies to:** all
- **Clause:** 9.1–9.7, 8.2.1, 8.2.4 [Class A, B, C]; 5.6.8 [Class B, C]; 5.7.2 [Class A, B, C]
- **Look for:** an issue tracker referenced from the repo (Trello links in PR templates or docs); problem reports that state criticality (effect on performance, safety or security, 9.1), the investigation and safety evaluation (9.2), and either a fix or a written reason for no action; affected parties told where needed (9.3). Changes start from an approved request (8.2.1; e.g. required PR review, protected `main`), with a traceable link between change, problem report and approval (8.2.4; e.g. ticket key in branch, PR title or commit). Bugs found in integration and system testing go into the same process (5.6.8, 5.7.2). Trend review of problems (9.6) and a check that each fix worked and caused no new problems, typically a regression test (9.7).
- **Met:** tracked with criticality, linked from changes, approved, with regression tests. **Partial:** tracked but not linked, or no criticality or safety evaluation. **Outside repo:** tracking happens only on Trello with no link from the repo.
- **Severity if not met:** Low

### SW-12 Maintenance plan, including updates and rollback
- **Applies to:** backend, tablet-app, monitoring
- **Clause:** 6.1, 6.2, 6.3 [Class A, B, C; 6.2.3: Class B, C]
- **Look for:** a written maintenance plan (6.1) with how feedback after release is received, recorded, evaluated, resolved and tracked; criteria for when feedback counts as a problem; use of the risk, problem and configuration processes; and how SOUP upgrades, patches and end-of-life are evaluated and applied. Feedback monitored from users and inside the team (6.2.1), each problem report judged for its safety effect, change requests analysed for their effect on deployed hospitals and connected systems (6.2.3) and approved (6.2.4). A way to tell hospitals about problems, the risk of carrying on unchanged, and how to get and install the fix (6.2.5). Changes re-released through the normal release process (6.3.2). In repos: deploy and promote workflows, rollback steps, a documented update procedure for hospitals.
- **Met:** a documented procedure covering these points, including rollback and user notification. **Partial:** automation exists but is undocumented, or no SOUP-update or user-notification procedure. **Gap:** none.
- **Severity if not met:** Medium

### SW-13 Common defects of the chosen languages identified and guarded against
- **Applies to:** backend, tablet-app, monitoring
- **Clause:** 5.1.12 [Class B, C]
- **Look for:** a written list of defect types typical for the technologies used (Python, Django, PySide6, React), e.g. `None` reaching a calculation, float rounding, unit mix-ups, unvalidated JSON input, UI-thread blocking, SQL or template injection, timezone errors; and evidence that each is prevented or caught: linters, type checkers, security scanners (`ruff`, `mypy`, `bandit`, `eslint`) in CI, coding rules, targeted tests. Tools running without a written defect list count as partial.
- **Met:** defect list with matching controls and evidence. **Partial:** tools or rules in place but no defect list, or a list without evidence. **Gap:** neither.
- **Severity if not met:** Medium

### SW-14 Detailed design for safety-critical units
- **Applies to:** backend, tablet-app
- **Clause:** 5.4.2–5.4.4 [Class C]
- **Look for:** for each unit, a design detailed enough to implement it correctly, including its interfaces with other units and outside parts, and a check that the design matches the architecture. Focus on the safety-critical areas in `innutrire-context.md` (feature preparation, BMI and temperature classes, injury factor, score forms, local cache). Design docs, or thorough module and function docstrings that state inputs, outputs, units and limits, can count. Applies while no class is recorded (4.3 g).
- **Met:** detailed design for the critical units, checked against the architecture. **Partial:** some units, or docstrings without stated limits. **Gap:** none. **Not applicable:** Class A or B recorded under SW-01.
- **Severity if not met:** Medium

### SW-15 Integration plan and integration testing
- **Applies to:** backend, tablet-app, monitoring
- **Clause:** 5.1.5, 5.6.1–5.6.8 [Class B, C]
- **Look for:** a plan for putting the software items (including SOUP) together and testing them as a whole, and tests that run the integrated parts: the tablet app against the real backend API (or a contract test of the API), the backend with the real model file and database, Moniteer against the agent endpoints. Tests should cover required functions, risk controls, interface behaviour and abnormal conditions such as network loss, server errors or bad input (5.6.4). Results recorded with failures and tester (5.6.7) and failures entered into problem tracking (5.6.8).
- **Met:** plan and integration tests across the main interfaces, with results. **Partial:** only within one repo (e.g. backend view tests with a test client), or no plan. **Gap:** none.
- **Severity if not met:** Medium

### SW-16 Test records kept for each release
- **Applies to:** backend, tablet-app, monitoring
- **Clause:** 5.7.5, 9.8 [Class A, B, C]; 5.6.7 [Class B, C]
- **Look for:** for system tests and for retests after a change, a lasting record of: which tests were run, pass/fail and failures found, the software version tested, test configuration and tools, the date, and who ran it (for automated runs, the workflow that triggered it). CI logs are a good source but GitHub Actions deletes them after its retention period (90 days by default), so check whether results are saved with the release (e.g. JUnit or coverage reports attached to the GitHub release). Manual test sessions on tablets need their own record.
- **Met:** test records with these details kept per release. **Partial:** only in CI logs that expire, or missing version or tester. **Gap:** no record.
- **Severity if not met:** Medium

### SW-17 Released software archived and delivered without corruption or tampering
- **Applies to:** backend, tablet-app, monitoring, provisioning, infrastructure
- **Clause:** 5.8.7, 5.8.8 [Class A, B, C]
- **Look for:** each released build and its documentation archived for at least the device's lifetime or the legal retention time, whichever is longer (5.8.7): release artefacts on GitHub releases, image registry tags that are not overwritten, a stated retention period. A delivery route that ensures what reaches the hospital is the released build, unchanged (5.8.8): checksums or code signing for the tablet installer, image digests rather than mutable tags, the provisioning and deploy scripts fetching a pinned release over an authenticated channel.
- **Met:** archived releases with a stated retention and a verified delivery route. **Partial:** archived but no integrity check on delivery, or no retention period. **Gap:** builds made or copied by hand with no archive.
- **Severity if not met:** Medium

### SW-18 Software causes of hazardous situations analysed and traced
- **Applies to:** backend, tablet-app (and monitoring if SW-01 does not exclude it); usually in the risk file
- **Clause:** 7.1–7.3 [Class B, C]
- **Look for:** in the risk file: which software items can contribute to each hazardous situation (7.1.1); for each, the possible causes, including wrong or incomplete specification, software bugs, SOUP failure or unexpected results, hardware or other software faults, and foreseeable misuse (7.1.2); the sequence of events (7.1.5). For each cause, a risk control (7.2.1); controls done in software listed as requirements (7.2.2). Each control verified, and checked for new hazards it could create (7.3.1). A trace from hazardous situation → software item → cause → control → verification (7.3.3). This is the software-level part of RM-01 and RM-03 under ISO 14971; score it on the software detail.
- **Met:** software items, causes, controls, verification and the full trace documented. **Partial:** hazards listed without software causes, SOUP causes or the trace. **Gap:** none.
- **Severity if not met:** High

### SW-19 Each change is checked for safety impact
- **Applies to:** all
- **Clause:** 7.4.1 [Class A, B, C]; 7.4.2, 7.4.3 [Class B, C]; 5.7.3 c)
- **Look for:** a step in the change process that asks whether a change (including a SOUP or model update) adds a new cause of a hazardous situation, needs a new risk control, or could weaken an existing one, with the risk file updated when it does. In repos: a PR template question on safety or risk impact, labels for safety-relevant changes, release notes noting risk review, dependency-update PRs that record a check.
- **Met:** a recorded safety check on changes, with risk file updates where needed. **Partial:** the question exists but answers are not recorded, or only for some change types. **Gap:** none.
- **Severity if not met:** Medium
