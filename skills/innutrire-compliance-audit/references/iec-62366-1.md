# IEC 62366-1:2015+AMD1:2020 (edition 1.1) — Usability engineering (key UE)

**Source:** checked against the full text of IEC 62366-1 edition 1.1 (2020-06, consolidated: 2015 first edition plus Amendment 1:2020). Clause numbers are exact.

**In plain words:** make sure busy staff can use the system without making dangerous mistakes. Write down who uses it, where and for what; list the screens and steps where a slip could hurt a patient; design those screens to prevent the slip; test early with a few real users while designing, then run a final test with representative users on the finished version; and keep all of it in one file.

**What the standard covers that matters for INNUTRIRE:**
- **Software counts, and so does the documentation.** The definition of usability engineering names software (3.17). The "user interface" includes every screen and also the accompanying documentation, such as instructions for use or a quick guide (3.26 Note 1).
- **A use error is any user action or lack of action whose result differs from what the maker intended or the user expected** (3.21). This includes not being able to finish a task. A software fault on its own is not a use error. Deliberate misuse ("abnormal use", 3.1) is out of scope, but an honest mistake is always in scope.
- **The process covers more than daily use** (4.1.1). It must cover every user interaction the documentation describes: installation, operation, maintenance and repair (and transport, storage and disposal, which mostly don't apply to software but should be ruled out on paper). The people doing it must be competent, and the development process must point to it.
- **Design first, warnings last** (4.1.2), in the same order as ISO 14971 7.1: 1) inherently safe design, 2) protective measures in the software, 3) information for safety and training. Annex A asks for the reason behind the option chosen.
- **Warnings and on-screen notes must be tested** (4.1.3). When information for safety (a warning, a label, an instructions-for-use note) is used as a risk control, it has to be shown to be noticed, understood and to lead to correct use by the intended users in the real setting.
- **The usability engineering file** (4.2) holds all records. It can be spread over other files (for example the risk management file) as long as it points to them.
- **Effort can be scaled** (4.3) by the size of the user interface, how severe the possible harm is, how wide the use specification is, whether part of the interface has no usability records (UOUP), and how big a change is.
- **Clause 5 is a chain of nine steps:** use specification (5.1) → safety-related interface features and possible use errors (5.2) → hazards and hazardous situations (5.3) → hazard-related use scenarios with their tasks and severity (5.4) → which scenarios go into the final test, with the reason (5.5) → user interface specification with testable requirements and a yes/no on whether instructions and training are needed (5.6) → evaluation plan, early and final (5.7) → design, build and early ("formative") evaluation (5.8) → final ("summative") evaluation on the finished version, with root-cause analysis of every use error and difficulty seen, then back to earlier steps or a residual-risk evaluation (5.9).
- **Training** (5.8): if training is needed for safe use, the maker must supply training materials or training (or enable the hospital to train its own staff) for the whole time the product is in service.
- **Interfaces built before the process** (5.10, Annex C): an unchanged older interface can be assessed by a shorter route (use specification, review of field information, check the risk analysis covers usability hazards, verify controls, re-evaluate residual risk). Any part that is changed, including to fix a usability problem, must go through 5.1 to 5.9.

**Relation to INNUTRIRE:** the main user interface is the tablet app: patient selection and patient forms, the REE calculation form, the severity score forms (APACHE, SOFA, SAPS, NUTRIC), the numeric keyboards, units (kg, cm, mL, °C), saved drafts, the result screen (REE versus energy recommendation) and the XAI screens. The sign-in and administration screens, the tablet setup scripts and server setup (installation and maintenance tasks) and Moniteer (used by INNUTRIRE staff) are also user interfaces under 4.1.1, with lower clinical stakes. Past field bugs (BMI labels, decimal severity scores, trauma level) are known use-error sources.

Check IDs UE-01 to UE-08 keep the same meaning as earlier versions of this checklist, because cards on the Trello board are matched by ID. New checks get new numbers.

### UE-01 Use specification
- **Applies to:** tablet-app, monitoring (normally one document for the whole system; a repo may link to it)
- **Clause:** 5.1 (also 3.23, 3.29, 3.20)
- **Look for:** a use specification (some regulators call it the "statement of intended use") with the six elements 5.1 names: medical indication (estimating energy needs of ICU patients); patient population (adult ICU, any exclusions such as children); part of the body interacted with (none: say so); user profile for each user group (ICU nurses, dietitians, doctors, hospital IT, INNUTRIRE support staff: training, language, experience with tablets); use environment (ICU bedside, gloves, interruptions, lighting, shift length, shared tablets); and operating principle (bedside data entry, model on the hospital server, offline cache). Search `README`, `docs/`, the shared compliance repo, and any instructions for use.
- **Met:** written with all six elements. **Partial:** some elements, or only implied in a README or the study protocol. **Gap:** none.
- **Severity if not met:** Medium

### UE-02 Safety-related user interface features and known use errors listed
- **Applies to:** tablet-app
- **Clause:** 5.2, 5.3
- **Look for:** a record (usability file, risk table or task analysis) that lists the screens, fields and steps where a mistake could harm a patient, the use errors that could happen at each (wrong patient picked, value typed in the wrong unit, decimal slip, wrong severity score answer, wrong trauma or burns level, resuming an old draft with stale readings, misreading the result), and the hazards and hazardous situations they lead to. 5.3 also asks that known problems with similar products and past use errors be considered: look for the past field bugs (BMI labels, decimal severity scores, trauma level) and their issue or PR links.
- **Met:** features, use errors and hazards listed, past bugs included. **Partial:** some areas, or bugs fixed in code with no usability record. **Gap:** none.
- **Severity if not met:** High

### UE-03 Units always shown and unambiguous
- **Applies to:** tablet-app, monitoring
- **Clause:** 5.6 (testable user interface requirements), 5.2, 4.1.2
- **Look for:** in `app/components/keyboards`, `app/components/score_forms`, `app/features/ree_calculation`, `app/features/predictive_equations`, `app/features/add_new_patient` and `app/features/edit_patient`: a unit label next to every numeric input and result, one unit per quantity everywhere (no kg on one screen and g on another), kcal and kcal/kg clearly separated, and the same units in Moniteer views of the same data. Units fixed by design (no unit choice) are stronger than a note telling users which unit to use.
- **Met:** every numeric field and result has a clear unit. **Partial:** some don't. **Gap:** units are often missing.
- **Severity if not met:** High

### UE-04 Input limits and validation messages
- **Applies to:** tablet-app (backend checks are covered by RM-04)
- **Clause:** 4.1.2, 5.6, 5.2
- **Look for:** minimum and maximum values on numeric inputs, decimal rules (how many places, whole numbers for scores), blocking or warning on out-of-range values, and messages that say what is wrong and what range is allowed. Check the priority order of 4.1.2: blocking an impossible value (design) beats a warning; a warning beats a line in the manual. Where only a warning is used, look for a recorded reason that blocking was not practicable.
- **Met:** all clinical inputs bounded by design, with clear messages. **Partial:** some inputs, or warning-only without a reason. **Gap:** free numeric entry.
- **Severity if not met:** High

### UE-05 Review step before a calculation is submitted
- **Applies to:** tablet-app
- **Clause:** 4.1.2 (protective measure), 5.6
- **Look for:** a review or summary screen showing the patient's name and the entered values (with units) before a prediction is saved; confirmation before a patient record is changed or deleted; soft delete or undo; and, when a saved draft is resumed, a clear sign of how old its readings are.
- **Met:** review step and soft delete. **Partial:** one of the two. **Gap:** neither.
- **Severity if not met:** Medium

### UE-06 Results and explanations are clear and hard to misread
- **Applies to:** tablet-app, monitoring
- **Clause:** 5.2 (displays; the software interprets data), 5.6, 4.1.3
- **Look for:** in `app/features/ree_calculation` and `app/features/xai`: clear separate labels for the predicted REE and the energy recommendation (they differ by the injury factor), which injury factor was applied, sensible rounding, units, the patient the result belongs to, and AI explanations (SHAP, feature importance) labelled as supporting information rather than a prescription. Text such as "use clinical judgement" is information for safety; see UE-11 for whether it has been tested.
- **Met:** clear. **Partial:** some ambiguity. **Gap:** values shown without labels or units.
- **Severity if not met:** High

### UE-07 Usability evaluation plan and records
- **Applies to:** tablet-app (records usually outside the repo)
- **Clause:** 5.7.1–5.7.3, 5.8, 5.9
- **Look for:**
  - **Plan (5.7):** the aim and method of each early and final evaluation; which user groups take part; test setting and conditions based on the use specification (gloves, interruptions, noise); whether the instructions are available and training is given before the test, and how long before.
  - **Formative records (5.8):** notes from early tests, expert reviews or walkthroughs with nurses or dietitians, which screens were tested, and what changed as a result.
  - **Summative records (5.9):** a test on the final or release-equivalent version, covering each scenario chosen under UE-09, with the definition of correct use for each, how participants represent the user profiles, every use error and difficulty seen ("close calls" included), its root cause, and the decision taken (redesign and return to 5.6, or a recorded reason no change is practicable plus a residual-risk evaluation per ISO 14971 7.3). The field study at 4 hospitals is a clinical study, not a summative usability test, unless its protocol says it collects these data.
- **Met:** plan, formative and summative records. **Partial:** formative only, or a plan without results. **Outside repo** if a link points elsewhere. **Gap:** none.
- **Severity if not met:** Medium

### UE-08 Usability engineering file
- **Applies to:** all (normally kept once for the whole system)
- **Clause:** 4.2
- **Look for:** one place that holds or points to all usability records: UE-01, UE-02, UE-07, UE-09 to UE-14. It may live inside the risk management file or the shared compliance repo, as long as there is an index that points to each record.
- **Met:** exists with pointers to every record. **Partial:** records exist but are scattered with no index. **Gap:** none.
- **Severity if not met:** Low

### UE-09 Hazard-related use scenarios described and chosen for the final test
- **Applies to:** tablet-app (usually in the usability or risk file)
- **Clause:** 5.4, 5.5
- **Look for:** for each hazard from UE-02, a written scenario: who does what, in which order, at which screen, and how severe the harm could be (for example: a nurse enters weight in grams on the REE form during a busy shift, the prediction is far off, the patient is underfed). Then the rule used to pick which scenarios go into the summative test (all of them, or a subset by severity of harm), the reason for that rule, and the resulting list.
- **Met:** scenarios with tasks and severity, plus a selection rule, reason and list. **Partial:** scenarios without severity or without a selection record. **Gap:** none.
- **Severity if not met:** Medium

### UE-10 User interface specification
- **Applies to:** tablet-app
- **Clause:** 5.6
- **Look for:** a written specification of the user interface (it can sit inside the software requirements) that is built from the use specification, the known use errors and the scenarios, and that holds testable requirements for the safety-related parts: units per field, input limits, decimal rules, review step, result labels, font size and contrast for bedside reading, touch target size for gloved use. It must also say yes or no to "are instructions for use needed?" and "is product-specific training needed?". Tests or UI tests that check these requirements are good supporting evidence.
- **Met:** specification with testable requirements and both yes/no decisions. **Partial:** requirements exist but are not tied to use errors, or the two decisions are missing. **Gap:** none.
- **Severity if not met:** Medium

### UE-11 Information for safety and instructions for use are provided and tested
- **Applies to:** tablet-app
- **Clause:** 4.1.3, 3.2, 5.8, 5.7.3 c)
- **Look for:** what users actually get: instructions for use, a quick reference card, in-app help or an about page, and on-screen warnings (model limits, "supporting information only", unit reminders). Where any of these is relied on as a risk control, look for evidence that it was checked to be noticed, understood and to lead to correct use by nurses and dietitians at the bedside (part of the summative plan). RM-12 checks that residual risks are disclosed; this check is about whether the material exists for users and works.
- **Met:** user material exists and safety-relevant parts were tested. **Partial:** material exists but was never tested, or exists only in developer docs. **Gap:** none.
- **Severity if not met:** Medium

### UE-12 Training decision and training materials
- **Applies to:** tablet-app (usually outside the repo)
- **Clause:** 5.6, 5.8, 5.7.3 d)
- **Look for:** a recorded decision whether product-specific training is needed for safe use. If yes: training materials or a training session for nurses and dietitians, or a train-the-trainer pack so each hospital can train new staff, kept available for as long as the product is in use (including when a new release changes a screen). The field study's site initiation or training records count as evidence.
- **Met:** decision recorded and, if needed, materials available. **Partial:** training given once with no lasting materials, or no recorded decision. **Outside repo** if kept elsewhere. **Gap:** none.
- **Severity if not met:** Medium

### UE-13 Screens built before the process are handled (UOUP)
- **Applies to:** tablet-app
- **Clause:** 5.10, Annex C (C.2.1–C.2.5), 4.3 d) and e)
- **Look for:** a decision on which existing screens have no usability records ("user interface of unknown provenance") and how each is handled. For unchanged screens, the Annex C route: use specification, review of field information (problem reports, field-study issues, past bugs), confirmation that the risk analysis covers their usability hazards, verified controls, and a residual-risk result. Screens that were changed since, or changed to fix a usability problem, must instead go through 5.1 to 5.9. Check release notes and `CHANGELOG.md` for UI changes that skipped this.
- **Met:** UOUP screens listed and assessed, changed screens in the full process. **Partial:** listed but not assessed, or changes made with no usability step. **Gap:** not considered.
- **Severity if not met:** Medium

### UE-14 Usability process, scope and level of effort are documented
- **Applies to:** all (usually in the shared compliance repo)
- **Clause:** 4.1.1, 4.3
- **Look for:** a documented usability engineering process that the development process (ISO 13485 clause 7 or the software development plan) points to; who does the work and why they are competent; which user interactions are in scope (bedside use, sign-in and staff administration, tablet installation via `tablet-setup-scripts`, server installation and maintenance via Ansible, Moniteer) and a recorded "does not apply" for transport, storage and disposal of a software-only product; and the reason for the chosen level of effort (size of the interface, severity of harm, legacy screens, size of the change).
- **Met:** process, scope and effort rationale documented. **Partial:** process exists but scope is limited to bedside screens without a reason, or no competence or effort rationale. **Gap:** none.
- **Severity if not met:** Low
