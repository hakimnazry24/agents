# ISO 14155:2020 — Clinical investigation of medical devices (key CI)

**Source:** checked against the full text of ISO 14155:2020 (third edition), the edition INNUTRIRE follows. Clause numbers are exact.

**In plain words:** how to run a study of a medical device on patients safely and properly: a written plan (the clinical investigation plan, CIP), ethics approval, informed consent, data that can be trusted and traced, monitoring, reporting of problems with the device, and a final report.

**What the standard covers that matters for INNUTRIRE:**
- **Software as a medical device** (Clause 1, Note 2): the study should show *analytical validity* (the software gives the right output for a given input), *scientific validity* (the output relates to the patient's real condition) and *clinical performance* (the output is clinically useful). For INNUTRIRE: the pipeline reproduces the validated model, REE relates to measured calorimetry, and the energy target helps care.
- **Data must be trustworthy** (7.8.1): accurate, attributable (who entered it), complete, legible and timely, and traceable through every version.
- **Corrections never hide the original** (7.8.2): every change is dated, attributed and explained where needed; the original entry stays visible. This applies to electronic records too.
- **Processed data must be comparable with the original** (7.8.2 b): INNUTRIRE averages vitals and derives BMI and temperature classes, so the raw entered values must be kept next to the derived ones.
- **Subjects are identified by a code** (7.8.2 c, 7.5.2): an unambiguous subject code links all of a patient's data; the link between code and name is held securely at the site. Reports and publications must not identify subjects (7.7, 8.4 d).
- **Electronic clinical data systems need validation and controls** (7.8.3): tested and validated; change control; backup and recovery; edit checks for logic and consistency; an audit trail with no deletion of entered data; protection from unauthorised access; a list of who has access with dates, privileges and removal; investigator sign-off; user training.
- **Device accountability** (7.9): which device (for software: which version) was used, where and when. The CIP must identify the device including its software version (A.2 c).
- **Labelling** (6.10): the investigational device or its instructions must say it is for use in a clinical investigation only, unless that is not required.
- **Adverse events and device deficiencies** (7.4, 10.8, Annex F): all are recorded. A device deficiency includes malfunctions, use errors and inadequate instructions (3.19).
- **Accounting for subjects** (7.10): every enrolled subject is accounted for, and withdrawals are recorded with the reason.
- **Monitoring** (6.7, 9.2.4): risk-based, and may include centralised review of data without visiting the site. Moniteer is a candidate tool for this.

**Relation to INNUTRIRE:** the field study at 4 hospitals (target 300 patients) compares AI predictions with indirect calorimetry. Much of the evidence (CIP, ethics approvals, signed consents, monitoring reports) lives outside the code, so many items here are `Outside repo`. The repo checks focus on data integrity, traceability of each record to a subject and a software version, and change control during the study.

Check IDs CI-01 to CI-08 keep the same meaning as earlier versions of this checklist, because cards on the Trello board are matched by ID. New checks get new numbers.

### CI-01 Clinical investigation plan and endpoints referenced
- **Applies to:** all
- **Clause:** 6.4, Annex A (A.5 objectives, A.6 design, A.7 statistics)
- **Look for:** a reference to the CIP, its primary endpoint (for example agreement between predicted and measured REE) and the statistical plan, including sample size reasoning and the holdout set.
- **Met:** referenced. **Outside repo:** not in the repo; ask for it.
- **Severity if not met:** High

### CI-02 Ethics approval, consent and registration
- **Applies to:** all
- **Clause:** 5.4, 5.6, 5.8, 7.1
- **Look for:** references to ethics approval per site, the consent process (including consent by a legally designated representative for unconscious ICU patients, 5.8.3.2) and study registration in a public database (NMRR or ClinicalTrials.gov). The backend's consent field counts as a technical control only.
- **Met:** referenced. **Outside repo** otherwise.
- **Severity if not met:** High

### CI-03 Study data integrity and audit trail
- **Applies to:** backend, tablet-app, monitoring
- **Clause:** 7.8.1, 7.8.2, 7.8.3 d) and f)
- **Look for:**
  - soft delete instead of hard delete (no deletion of entered data);
  - timestamps and the person who created or changed each record (attribution);
  - an audit trail of edits that keeps the original value visible (ties to CS-07);
  - validation of the link between a prediction and its gold standard;
  - detection of orphan or out-of-range records (edit checks);
  - offline-sync conflict handling that does not silently overwrite.
- **Met:** all of these. **Partial:** some. **Gap:** records can be changed or lost without a trace.
- **Severity if not met:** High

### CI-04 Source data and paper records reconciled
- **Applies to:** backend, monitoring
- **Clause:** 7.5.3, 7.8.2
- **Look for:** a way to record or reconcile data collected on paper outside the app, such as an import tool or a field marking the data source, and a written note of which data may be entered straight into the app as the source.
- **Met:** exists. **Gap:** none. **Outside repo** if this is handled by a manual procedure.
- **Severity if not met:** Medium

### CI-05 Device version known for every study record
- **Applies to:** backend, tablet-app, monitoring
- **Clause:** 7.9, A.2 c), D.6.1 d)
- **Look for:** whether each prediction stores the app version, backend version and AI model version used.
- **Met:** all three stored. **Partial:** some. **Gap:** none.
- **Severity if not met:** High

### CI-06 Changes during the study are controlled
- **Applies to:** backend, tablet-app
- **Clause:** 7.5.1
- **Look for:** a rule or record that changes to the device during the study (model swaps, calculation changes) are documented with a description, a justification, their possible impact on the study endpoints, and the affected documents: changelog entries, release notes or a model-change log.
- **Met:** documented with impact notes. **Partial:** changelog only. **Gap:** none.
- **Severity if not met:** Medium

### CI-07 Adverse events and device deficiencies can be reported
- **Applies to:** tablet-app, backend, monitoring
- **Clause:** 7.4, 10.8, Annex F
- **Look for:** an in-app or documented route to report device problems (malfunctions, use errors, confusing instructions) or adverse events, and error capture that reaches the team.
- **Met:** exists. **Partial:** technical error capture only. **Outside repo** for a clinical reporting procedure.
- **Severity if not met:** Medium

### CI-08 Training and holdout data separated and frozen
- **Applies to:** backend (it ships the deployed model and its training data in `innutrire/model/` and `innutrire/data/`)
- **Clause:** A.7
- **Look for:** next to the deployed model: a documented, fixed holdout set; a check for patient overlap between the training and test sets; dataset version identifiers.
- **Met:** all of these. **Partial:** a holdout set but not frozen or versioned. **Gap:** none.
- **Severity if not met:** High

### CI-09 Raw entered values are kept next to derived values
- **Applies to:** backend, tablet-app
- **Clause:** 7.8.2 b)
- **Look for:** whether the stored prediction keeps every value the user entered (all repeated vital readings, height and weight with their units, score answers) and not only the averaged or classified features sent to the model, so an auditor can recompute the result from the source.
- **Met:** raw inputs stored with the result. **Partial:** some raw inputs lost (e.g. only averages kept). **Gap:** only model features stored.
- **Severity if not met:** High

### CI-10 Subjects are identified by a study code, not by identity
- **Applies to:** backend, tablet-app, monitoring
- **Clause:** 7.5.2, 7.7, 7.8.2 c), 8.4 d)
- **Look for:** an unambiguous subject or study code on every study record; whether data leaving the hospital server (Moniteer snapshots, exports, logs, reports) carries names, RNs or dates of birth; and where the code-to-patient link is kept.
- **Met:** study code used and identity stays at the site. **Partial:** a code exists but identifying fields still leave the site. **Gap:** records are linked only by name or RN.
- **Severity if not met:** High

### CI-11 Access to the clinical data system is listed and controlled
- **Applies to:** backend, monitoring, infrastructure
- **Clause:** 7.8.3 g) and h), 7.6
- **Look for:** personal accounts; a list of everyone with access, with the date access was given, the role or privileges, and the date it was removed; that removed users can no longer sign in. Compare with the study's site team log (who is authorised to enter data).
- **Met:** access list with dates and privileges, removal recorded. **Partial:** accounts exist but grant or removal dates are not kept. **Gap:** shared or anonymous access.
- **Severity if not met:** Medium

### CI-12 Clinical data is backed up, recoverable and retained
- **Applies to:** backend, infrastructure, monitoring
- **Clause:** 7.8.3 a) and j), 8.6, A.8 f) and g)
- **Look for:** scheduled database backups, a tested restore procedure, where backups are kept, and a stated retention period for study data.
- **Met:** backup, tested restore and retention period. **Partial:** backups without a tested restore or a retention period. **Gap:** no backups.
- **Severity if not met:** High

### CI-13 Clinical data system is validated
- **Applies to:** backend, tablet-app
- **Clause:** 7.8.3 a) to c), e)
- **Look for:** written requirements for how the system receives and processes study data, and evidence that they were tested (test suites, release test records, validation report), including that reports and exports are accurate.
- **Met:** requirements traced to passing tests. **Partial:** tests exist but no written requirements or validation record. **Gap:** none.
- **Severity if not met:** Medium

### CI-14 Software output reproduces the validated model (analytical validity)
- **Applies to:** backend
- **Clause:** 1 (Note 2, software as a medical device)
- **Look for:** tests that run fixed reference inputs through the full deployed pipeline (feature preparation, scaler, model, injury factor) and check the REE and energy target against expected values from the validated model, so a refactor or library upgrade can't silently change results.
- **Met:** reference-value tests for the full pipeline. **Partial:** tests of parts only. **Gap:** none.
- **Severity if not met:** High

### CI-15 Investigational use is labelled
- **Applies to:** tablet-app
- **Clause:** 6.10
- **Look for:** a statement on the app (splash, about or result screen) or in its instructions that the software is for use in a clinical investigation only, or a recorded reason why it is not required.
- **Met:** labelled. **Gap:** no such statement and no reason recorded.
- **Severity if not met:** Medium

### CI-16 Subject withdrawal is recorded
- **Applies to:** backend, tablet-app
- **Clause:** 5.8.5 c), 7.10
- **Look for:** a way to record that consent was withdrawn, with the date and reason when given, and that later data collection for that patient is blocked or flagged while existing data is kept as the consent allows.
- **Met:** withdrawal, date and reason recorded and enforced. **Partial:** a consent flag only, no date or reason. **Gap:** no way to record it.
- **Severity if not met:** Medium

### CI-17 Software deployment record for each site
- **Applies to:** provisioning, infrastructure, monitoring
- **Clause:** 7.9
- **Look for:** a record of which app, backend and model version is installed on each tablet and server, at which hospital, from which date to which date, including rollbacks.
- **Met:** kept per device with dates. **Partial:** current versions visible (e.g. in Moniteer) but no history. **Gap:** none.
- **Severity if not met:** Medium
